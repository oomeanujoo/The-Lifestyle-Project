- **2026-09-19 — Codex-assigned task (`agent-tasks/claude-04-task.md`): a real road-route provider (OSRM demo) behind a new Travel port, with a deterministic fuel-cost estimate and an honest fallback to the existing straight-line comparison.** Full detail in `agent-tasks/claude-04-result.md`; `TECHNICAL_ARCHITECTURE.md` §17.6 has the implemented-behavior summary. This entry is the reasoning.
  **Why a separate endpoint (`/routes/recommend-road`) instead of changing `/routes/recommend`**: Cline's own in-flight task owns the Travel UI's single-search contract against the existing `/recommend` response shape. Changing that shape mid-flight would risk breaking work happening in parallel on the personal PC — additive-only was the safer call, and the task itself allowed either approach.
  **Why this is the first genuinely external HTTP call travel-service makes on its own**: every prior travel-service outbound call went through `integration-service` (the single owner of `lifestyle_master`, §17/§20) — travel-service itself never called GeoNames/Frankfurter/an AI provider directly. OSRM is different in kind: it's not master data, it's a real-time routing query keyed on two arbitrary coordinates, which doesn't fit the "central master, single owner" model at all. Calling it directly from travel-service, behind its own `RoadRouteProvider` port, keeps the single-owner rule intact for actual masters while still getting real road data into the Travel demo.
  **A real bug caught before it shipped, not found later**: the first version of `OsrmRoadRouteProvider` built its own `RestClient` with a custom `SimpleClientHttpRequestFactory` for a dedicated OSRM timeout, mutating a `RestClient.Builder` obtained from the shared, singleton `RestClientConfig` bean. Since that bean is a singleton and `RestClient.Builder`'s configuration methods mutate the same instance, this would have silently applied OSRM's short demo-server timeout to every other class that happens to be constructed after it and injects the same builder (`IntegrationMasterDataClient`) — a real, order-dependent bug, not a hypothetical one. Fixed by dropping the custom request factory entirely and matching the established `GeoNamesClient`/`FrankfurterClient` pattern exactly (inject the shared builder, call `.build()`, nothing else) — simpler, consistent with the rest of the codebase, and it also made the class properly testable with `MockRestServiceServer`, which the timeout-mutation version would have fought.
  **Why the fuel-cost estimate is deliberately narrow**: the task said explicitly that AI may explain a sourced result but never calculate one, and that this estimate must exclude tolls/parking/live prices unless a verified provider supplies them — no such provider exists here. `FuelCostEstimate.compute()` is plain arithmetic over three explicit config values, and its own `label` field states the exclusion outright in the API response itself, not just in a doc, so a caller can't mistake it for a total trip cost without being told.

- **2026-09-19 — Codex-assigned task (`agent-tasks/claude-03-task.md`): closed the gap between "the master refresh button exists" and "it gives single-owner-quality coverage" — bulk Indian city discovery, all-currency import, and an honest UNSUPPORTED status for masters with no source at all.** Full file-by-file detail in `agent-tasks/claude-03-result.md`; `TECHNICAL_ARCHITECTURE.md` §17.5.1 has the implemented-behavior summary. This entry is the reasoning.
  **Why city discovery is "search by country + population," not "search more names"**: the previous refresh only ever looked up cities whose names were already hand-typed into `app.masters.seed-cities` — a real ceiling of ~6 cities no matter how many times it ran. GeoNames' `searchJSON` supports filtering by `country`+`featureClass=P` (populated place) with `orderby=population`, which returns real, ranked results without the caller needing to already know a single name — the same kind of shift travel-service's live place search made earlier this session (stop searching a hardcoded name list, start querying the actual source). Paging via `startRow` and bounding by `indiaCityTargetCount`/`indiaCityMaxPages` keeps this a deliberate, credit-bounded call, not an unbounded scrape.
  **Why currency dropped `tracked-currencies` entirely rather than expanding the list**: the task said "import all valid currencies," and Frankfurter's own documented behavior for an omitted `symbols` parameter is exactly that — returning its complete supported set for a base currency. Keeping a "tracked" shortlist around after removing its only real purpose (deciding what counts as PARTIAL) would have been dead config with no reader left to justify it.
  **Why `UNSUPPORTED` is synthesized at read time instead of written to `master_refresh_log`**: `visa_requirement`/`municipality`/`area`/`locality`/`pincode` have never had a refresh attempt to log — writing a fake log row to represent "no attempt happened" would itself be exactly the kind of fabricated-record problem this project's rules exist to prevent (§10).   **What stayed the same, deliberately**: the AI-drafted-proposal path for `transport_mode`/`bhk_type`/`service_addon` (built the previous task) already satisfied "the AI acquisition path may propose additional values, but proposals stay DRAFT until explicit acceptance" — no change needed there, and `refreshAll()` deliberately still does not auto-trigger AI acquisition on every Settings-page click (that stays a separate, explicit `POST .../acquire` call, so an AI provider call is never a surprise side effect of routine master refresh).

- **2026-09-19 — Codex-assigned task (`agent-tasks/claude-next-task.md`): "backend AI master engine" — versioned prompt definitions per master type, a full prompt-to-DRAFT-proposal flow for `bhk_type`, and a distinction in what "acceptance" means depending on whether a master is flat/FK-free or hierarchical.** Full detail (files changed, endpoints, test results) is in `agent-tasks/claude-next-result.md`; §17.5 of `TECHNICAL_ARCHITECTURE.md` has the implemented-flow summary. This entry is the *why*.
  **Why prompt definitions are files, not Java string literals**: the task asked for "purpose, scope, required fields, field formats, allowed values or code rules, evidence requirements, an example response" per master type — that's naturally structured data, not code, and keeping it in versioned JSON files (`{masterType}.v{n}.json`, loaded by one small `PromptRegistry` at startup) means a wording change or a new master type never touches Java at all. Versioning matters because a prompt is now recorded provenance on every proposal it produces — a later, better-worded v2 must never retroactively change what a v1-era proposal was judged against.
  **Why `bhk_type` first, and why `transport_mode`/`service_addon` "already work" without extra code**: all three are the exact same shape through the existing `CodedMasterRepository`/`CodedMasterType` abstraction (§10's generic-over-bespoke rule, already built before this task) — `MasterAcquisitionUseCase.acquire(CodedMasterType)` never special-cases which one it's given. Building it once, correctly, for `bhk_type` and letting the enum parameter do the rest is "making the pattern reusable without a large generic framework," read literally, not a partial implementation of the other two.
  **Why "verified" means a fixed rule check, never the model's word or provider agreement**: the task said this explicitly, and it matches this codebase's existing stance (§10 — "AI never asserts a fact," `suggestPlacesVerified()`'s own comment on provider agreement not being proof). Each prompt definition carries either a closed `allowedValues` list (`bhk_type`, `transport_mode` — a small, real, enumerable domain) or a `codeFormatRegex` (`service_addon` — open-ended, so only the *format* is checkable, not that the addon itself is universally standard, which the prompt file says outright). A candidate that doesn't match is rejected outright, never proposed as "AI thinks so."
  **Why acceptance behaves differently for coded masters vs. `visa_requirement`/the locality hierarchy — the one deliberate asymmetry in this design**: reusing one `master_proposal` table for both kinds of "AI idea with no verified provider" was right per §10, but treating their acceptance identically would have been wrong. `bhk_type`/`transport_mode`/`service_addon` are flat rows with one uniqueness constraint (`code`) and a repository method that already exists and is already safe to call generically. `locality` requires a real `area`→`municipality`→`city` chain that a generic accept step has no way to safely construct or validate — auto-writing there on acceptance would risk exactly the kind of fabricated/inconsistent master row this whole task explicitly rules out. So `MasterProposalUseCase.accept()` checks `CodedMasterType.fromMasterName(...)`: present → write the real row first, flip to ACCEPTED only if that succeeds (never ACCEPTED with no matching row); absent → status-only, matching the earlier task's already-documented reasoning.
  **Real bug hit and fixed along the way, not proactively predicted**: `ObjectMapper` (needed for parsing AI JSON output and `proposedData`) had no autoconfigured bean either — the exact same Spring Boot 4.1.1 modularization gap already found for `RestClient.Builder` earlier this session. Caught immediately because this session now runs real tests against a real downloaded JDK 25 (see the earlier `RestClient.Builder` entry) instead of only the Java-8-toolchain-gap check — fixed with the same pattern, an explicit `@Bean ObjectMapper` in a new `JacksonConfig`.
  *Why this matters going forward*: any future AI-driven master type (city/currency prompt definitions already exist, undocumented-only, for exactly this reason) can reuse `MasterAcquisitionUseCase` as-is if it's a `CodedMasterType`, or the plain `MasterProposalUseCase.propose()` path if it isn't — no new generic framework should be built until a third *kind* of acceptance behavior is actually needed, not just a third master type.
